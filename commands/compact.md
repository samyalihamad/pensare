## Directory Structure

Projects are organized in `~/.claude/contexts/`:

```
~/.claude/contexts/
├── my-project/
│   ├── sources.json          # Source URLs, sync config, publish targets
│   ├── journal/              # Hot journal (rolling ~30 days)
│   │   ├── manifest.json     # Structured index for all tiers
│   │   ├── 2026-W17.md       # Weekly journal file
│   │   └── archive/          # Processed hot files (kept for recovery)
│   ├── kb/                   # Knowledge base (topic-partitioned, from compaction)
│   │   └── auth-migration.md
│   └── Overview.md           # Context file (generated by sync)
├── another-project/
│   ├── sources.json
│   └── Plan.md
└── standalone.md             # Legacy flat files still supported
```

# Compact — Journal Compaction and Migration

Arguments: $ARGUMENTS

Compacts the journal: migrates legacy `journal.md` to the three-tier format, ages out hot entries older than the retention window into topic-based knowledge base files.

## Steps

### Step 1: Resolve Project

Same pattern as note/checkpoint:
- Check session context, known project name in args, single project auto-resolve, or ask

### Step 2: Migrate Legacy Journal (if needed)

If `journal.md` exists at the project root AND `journal/` directory does NOT exist:

1. Create directories: `mkdir -p ~/.claude/contexts/{project}/journal/archive/` and `mkdir -p ~/.claude/contexts/{project}/kb/`
2. Read `journal.md` in full
3. Parse entries by `### {date} — {tag}: {summary}` headers. Each entry runs from one header to the next.
4. Split entries into two sets based on their date:
   - **Hot** (within last 30 days): Group by ISO 8601 week, write each group to `journal/{week}.md` with header `# Journal — Week of {Monday date}`
   - **Cold** (older than 30 days): Hold for distillation in Step 5
5. Create `journal/manifest.json` with `hot_files` entries for each week (entries count, date_range, tags, one_line)
6. Set `legacy_journal_migrated: true` in manifest
7. Rename `journal.md` to `journal.md.bak` (backup until compaction completes)
8. Print: "Migrated {N} entries from legacy journal.md — {H} hot, {C} cold"

### Step 3: Manifest Integrity Check

Verify manifest consistency with files on disk (makes compaction idempotent and safe to retry after crashes):
1. Scan `journal/*.md` files (exclude `manifest.json` and `archive/` directory)
2. If any `.md` file exists on disk but is NOT in `manifest.hot_files`, reconstruct its entry (parse headers to get entries count, date_range, tags)
3. If any `manifest.hot_files` entry references a file that doesn't exist on disk, remove it
4. If `compaction_in_progress` is `true` from a previous crashed run, print warning: "Recovering from interrupted compaction — re-processing."

### Step 4: Identify Expired Hot Entries

1. Read `manifest.json`. Read `hot_retention_days` from manifest (default 30 if missing).
2. Set `compaction_in_progress: true` in manifest and write it
3. Identify hot files with `date_range` end date older than `hot_retention_days` days from today
4. If no expired entries exist, set `compaction_in_progress: false`, write manifest, print "Nothing to compact — all entries within retention window." and stop.

### Step 5: Distill into Knowledge Base (Agent-Driven)

If there are expired entries to distill:

1. Read each expired hot file in full
2. Read existing KB files from `kb/` directory (if any) — read FULL content of each
3. Read existing `kb_files` entries from manifest
4. Spawn a subagent (model: `sonnet`) with this prompt:

---

You are reorganizing journal entries into a topic-based knowledge base for efficient lookup. The goal is ORGANIZATION, not compression. Every piece of actionable knowledge must be preserved — the reader should never need to go back to the original journal entries.

## Existing KB files:
{For each KB file: filename, one_line from manifest, then FULL current content}

## Expired journal entries to organize:
{Full text of all expired entries}

## Instructions:

For each entry, determine which KB topic it belongs to:
- If an existing KB file covers this topic, REVISE that file — integrate new information into existing content. Your output REPLACES the file entirely (overwrite semantics).
- If no existing KB file fits, CREATE a new one with a descriptive kebab-case filename (e.g., `auth-migration.md`, `api-design-decisions.md`)
- Each KB file MUST be under 150 lines. If a topic grows beyond that, split into sub-topics.

## What to PRESERVE VERBATIM (never summarize these):
- Step-by-step workflows, runbooks, and command sequences
- Exact CLI commands with flags and arguments
- Workarounds and their specific steps
- Error messages and their exact fixes
- Configuration values, flag names, environment variables
- Code file paths with line numbers
- PR/issue IDs, ticket numbers, commit hashes
- People names and their responsibilities
- Decisions with their rationale

## What to CONDENSE (merge related items, remove noise):
- Narrative about debugging attempts that led to dead ends (keep the conclusion, drop the journey)
- Conversational tone and session context ("I then tried...", "After discussing with...")
- Duplicate information already captured in another entry or KB file
- Timestamps and session metadata (unless part of a timeline that matters)

## Key principle:
If someone asks "how do I do X?" or "what's the workaround for Y?", the KB file must have the COMPLETE answer with exact commands. They should never need to ask "but what were the exact flags?"

For each KB file you write or update, output a manifest entry:
- file: the filename
- topic: human-readable topic name
- entities: list of key identifiers AND their common aliases/synonyms. Include terms a user might search for.
- date_range: [oldest date, newest date] of entries that contributed
- one_line: 1-sentence summary (max 120 chars)

Output format — FOLLOW THIS EXACTLY:
1. For each KB file, print the FULL file content between markers:
   --- FILE: {filename} ---
   {full file content — this overwrites the existing file}
   --- END FILE ---

2. After all files, print manifest entries as a valid JSON array:
   --- MANIFEST ---
   [{entries}]
   --- END MANIFEST ---

---

5. Parse the subagent output:
   - Look for `--- FILE: {filename} ---` and `--- END FILE ---` markers. Extract filename and content.
   - Look for `--- MANIFEST ---` and `--- END MANIFEST ---` markers. Parse JSON array.
   - **If parsing fails** (markers missing, invalid JSON): Write all expired entries verbatim to `kb/uncategorized-{YYYY-MM}.md`. Create a manifest entry: `{"file": "uncategorized-{YYYY-MM}.md", "topic": "Uncategorized ({month name} {year})", "entities": [], "date_range": [...], "one_line": "Raw entries — compaction parsing failed, needs manual review"}`. Print a warning.
   - Write/update each KB file to `kb/{filename}` (overwrite, not append)
   - Merge new `kb_files` entries into manifest (update existing entries by matching filename, add new ones)

### Step 6: Cleanup

1. Create `journal/archive/` if it doesn't exist
2. Delete any files already in `journal/archive/` from a PREVIOUS compaction cycle (keeps one cycle of archives for safety)
3. Move processed hot files to `journal/archive/` (source data preserved for recovery)
4. Remove archived files from `hot_files` in manifest
5. Merge new `kb_files` entries into manifest
6. Set `compaction_in_progress: false` and update `last_compaction` to current ISO timestamp
7. Write manifest atomically: write to `journal/manifest.json.tmp`, verify it's valid JSON, then rename to `journal/manifest.json`
8. Delete `journal.md.bak` if it exists (legacy migration confirmed complete)
9. If git mode (`storage: "git"` in `sources.json`), auto-commit:
   ```bash
   cd {git_path} && git add journal/ kb/ && git commit -m "pensare compact: {N} entries -> {M} KB files" && git push
   ```

### Step 7: Update MEMORY.md Pointers

After compaction, scan the user's MEMORY.md (`~/.claude/projects/*/memory/MEMORY.md`) for stale journal references:
1. Find any references to `journal.md` or `journal entry YYYY-MM-DD` that now correspond to content in KB files
2. Update those pointers to reference the KB file path instead (e.g., `See journal entry 2026-04-07` becomes `See kb/auth-migration.md`)
3. If a MEMORY.md entry references a journal date that falls within a KB file's `date_range` and matches its `entities`, update the pointer
4. Only update pointers — do NOT remove or rewrite MEMORY.md content

### Step 8: Report

Print report:
```
Compaction complete:
- Migrated: {N} entries from legacy journal.md (if applicable)
- Compacted: {N} expired entries from {M} weekly files
- Archived: {M} hot files moved to journal/archive/
- KB files updated: {list}
- KB files created: {list}
- Hot journal: {N} entries across {M} weeks remaining
```
